# Pulse task #2333: Create tracks and add devices by dropping onto track lanes

Operation: a8ceae757bd85f04d1091e2b3d7a9142
Assignee: PORTALSURFER (Pulse #1, GitHub ID 41680373)

User-requested native device-browser workflow for Arrangement track lanes. Extend device drag-and-drop beyond the existing fixed device rail/card targets (related Hex #2136 and instrument-card replacement #2262). Use the existing canonical track/device model and controller commands; do not introduce a new track type, DSP behavior, or audio-routing policy.

Acceptance:
- Empty Arrangement space: dropping a registered browser device creates a new track and assigns that device to it. For an instrument, populate the track's instrument slot; for an effect, place it in the device/effect chain according to established model semantics. Track creation and device assignment are one atomic, undoable operation; failed, stale or cancelled drops leave the project unchanged.
- Gap between tracks: dropping at the gap creates a new track at that exact ordering position with the device assigned. Existing track order, device state, clips and selection are preserved except for the intended insertion; one Undo removes the inserted track and restores prior state.
- Existing track lane: dropping an effect adds it to that track's effect chain using established insertion behavior. Dropping an instrument targets that track's instrument slot: insert it if empty or replace the current instrument if occupied, preserving the track, effect chain and clip content. Instrument replacement is atomic and Undo restores the prior instrument.
- Render clear insertion previews for empty space, between-track gaps and track lanes. Validate wrong/stale target, project-generation/revision changes, cancellation and unsupported devices fail visibly and atomically. Do not let a track-lane instrument drop silently create an extra instrument or replace an effect.
- Add focused controller/service and rendered-pointer coverage for all three destinations, instrument/effect routing, insertion order, replacement, Undo and refusal cases; run the project's local CI and provide a fresh user-review build.

The default chain position and post-drop focus/selection should follow existing Hex conventions. If no convention exists, record that as a focused implementation-time decision instead of inventing new sound, track-type or routing semantics. No implementation in this planning ticket.

User clarification: the track-lane device drag should feel very similar to dragging and dropping samples. Reuse the established sample-drop affordances and placement semantics for lane targeting, insertion preview, track creation/insertion, cancellation and drop feedback wherever they apply; retain device-specific behavior for instrument-slot insertion/replacement and effect-chain addition. Do not change sample handling or invent a new track/drop model.
